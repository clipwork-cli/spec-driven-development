# Runtime Context

---

# Purpose

Runtime Context describes how the application behaves when it is executing.

Its purpose is to provide engineers and AI agents with a shared understanding of business capabilities, execution flow, operational behaviour and system interactions.

Runtime Context should answer

> "How does this application work?"

It complements Repository Context.

Repository Context explains how the repository is engineered.

Runtime Context explains how the application behaves.

---

# Scope

Runtime Context covers

- Business Capabilities
- Runtime Execution Flow
- Operational Workflows
- Integrations
- Data Flow
- Observability
- Runtime Risks

Runtime Context does not describe repository structure.

Repository structure belongs to Repository Context.

---

# Documents

## capabilities.md

Defines the Business Capabilities supported by the application.

Examples

- Asset Search
- Reporting
- User Management
- Synchronisation

Business Capabilities become the units used by the Architect when generating Specifications.

---

## runtime-flow.md

Describes how requests move through the application.

Examples

HTTP Request

↓

Authentication

↓

Controller

↓

Application Service

↓

Repository

↓

Database

Includes major execution paths.

---

## operations.md

Describes operational behaviour.

Examples

- Scheduled Jobs
- Background Workers
- Batch Processing
- Queue Consumers

Operations represent recurring runtime activities.

---

## integrations.md

Describes interactions with external systems.

Examples

- Oracle
- SAP
- Azure
- Kafka
- REST APIs

Focus on runtime interactions rather than implementation.

---

## data-flow.md

Describes how information moves through the application.

Examples

Request

↓

Validation

↓

Business Logic

↓

Database

↓

External Systems

↓

Response

Include important persistence and messaging flows.

---

## observability.md

Documents runtime monitoring.

Examples

- Logging
- Metrics
- Tracing
- Health Checks
- Alerts

Focus on runtime diagnostics.

---

## runtime-risks.md

Documents runtime engineering risks.

Examples

- Long-running transactions
- Single points of failure
- Missing retries
- High latency
- Operational bottlenecks

---

# Ownership

Runtime Context is generated by

Runtime Discovery.

Unlike Repository Context

Runtime Context may evolve more frequently as business capabilities change.

---

# Consumers

Runtime Context is consumed by

- Architect
- Planner
- Developer
- Reviewer

The Architect relies heavily on Runtime Context to define Business Capability boundaries.

---

# Relationship with Repository Context

Repository Context explains

> How the repository is built.

Runtime Context explains

> How the application behaves.

Neither replaces the other.

Both are required before Specification generation.

---

# Engineering Principle

Repository Context

↓

Runtime Context

↓

Specification

↓

Planning

↓

Implementation

↓

Review

Knowledge should always precede implementation.

---

# Success Criteria

Runtime Context is complete when

✓ Business Capabilities identified

✓ Runtime flows documented

✓ Operational workflows documented

✓ Integrations documented

✓ Data flows documented

✓ Observability documented

✓ Runtime risks documented

✓ Application behaviour understood
