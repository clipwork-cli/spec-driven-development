# Oracle to PostgreSQL Translation Rules

**Version:** 1.0

---

# Purpose

This document defines the engineering rules for translating Oracle database artifacts into PostgreSQL.

These rules are consumed during implementation of a business capability.

The objective is to preserve business behaviour while producing PostgreSQL-compatible implementations.

Translation should always be validated against the provided PostgreSQL schema.

---

# Engineering Principles

Every translation should follow these principles.

1. Preserve behaviour.
2. Prefer PostgreSQL-native syntax.
3. Never invent schema objects.
4. Validate against the supplied PostgreSQL schema.
5. Preserve transaction semantics.
6. Preserve null behaviour.
7. Preserve data integrity.
8. Document assumptions.

---

# Translation Workflow

Every database object should follow the same workflow.

```
Identify

↓

Locate PostgreSQL Schema

↓

Translate

↓

Validate

↓

Test

↓

Review
```

Do not skip validation.

---

# Translation Scope

AI may assist with translating

- Inline SQL
- Stored Procedures
- Functions
- Views
- Packages
- Repository Queries
- Dapper SQL
- ADO.NET SQL

AI should not redesign

- Schema
- Indexes
- Constraints
- Partitioning
- Performance Strategy

---

# Required Inputs

Before translation begins

the following inputs must exist.

- Repository Context
- Runtime Context
- PostgreSQL Schema
- Business Capability Specification

If any are missing

stop

and request them.

---

# Schema Rules

Always use

the supplied PostgreSQL schema.

Never

- create tables
- rename tables
- rename columns
- infer relationships
- modify data types

If schema conflicts exist

report them.

Do not attempt to resolve them automatically.

---

# General SQL Rules

Prefer PostgreSQL-native syntax.

Avoid Oracle compatibility layers.

Preserve

- filtering
- ordering
- transactions
- locking
- null behaviour

---

# Oracle Function Mapping

| Oracle         | PostgreSQL        |
| -------------- | ----------------- |
| NVL            | COALESCE          |
| NVL2           | CASE              |
| DECODE         | CASE              |
| SYSDATE        | CURRENT_TIMESTAMP |
| SYSTIMESTAMP   | CURRENT_TIMESTAMP |
| USER           | CURRENT_USER      |
| LENGTH         | LENGTH            |
| SUBSTR         | SUBSTRING         |
| INSTR          | POSITION          |
| TRUNC(Date)    | DATE_TRUNC        |
| ADD_MONTHS     | + INTERVAL        |
| MONTHS_BETWEEN | AGE               |
| TO_CHAR        | TO_CHAR           |
| TO_DATE        | TO_DATE           |

When multiple PostgreSQL alternatives exist

prefer readability.

---

# Pagination

Oracle

```
ROWNUM
```

should become

```
LIMIT

OFFSET
```

Maintain deterministic ordering.

Never paginate without ORDER BY.

---

# Sequences

Prefer

```
GENERATED BY DEFAULT AS IDENTITY
```

when compatible with the supplied schema.

If sequences already exist

reuse them.

Do not redesign identifier generation.

---

# MERGE Statements

Translate Oracle MERGE statements into

```
INSERT ...

ON CONFLICT ...

DO UPDATE
```

Validate

- unique constraints
- conflict targets
- update behaviour

---

# Stored Procedures

Translate procedures using

PL/pgSQL.

Preserve

- parameters
- transactions
- exceptions
- return values

If Oracle-specific packages are referenced

document manual work required.

---

# Packages

Oracle Packages have no direct PostgreSQL equivalent.

Recommended approaches

- Functions
- Schemas
- Application Services

Do not automatically redesign packages.

Escalate architectural decisions.

---

# Views

Translate using the supplied PostgreSQL schema.

Validate

- joins
- aliases
- aggregates
- functions
- filters

Document unsupported Oracle syntax.

---

# Triggers

Translate trigger logic

only when required by the migrated business capability.

Preserve

- timing
- event
- transactional behaviour

If behaviour cannot be preserved

escalate.

---

# Inline SQL

Translate

- SELECT
- INSERT
- UPDATE
- DELETE

Validate

- parameters
- null handling
- joins
- ordering
- paging

Avoid unnecessary query rewrites.

---

# Transactions

Preserve

- isolation behaviour
- commit behaviour
- rollback behaviour

Do not optimise transaction boundaries during migration.

---

# Null Handling

Null behaviour should remain identical.

Pay particular attention to

- NVL
- comparisons
- concatenation
- aggregate functions

---

# Date and Time

Validate

- timezone behaviour
- precision
- date truncation
- interval calculations

Never assume server timezone.

---

# Boolean Behaviour

Oracle frequently represents Boolean values using

```
NUMBER

CHAR

VARCHAR2
```

Translate according to the supplied PostgreSQL schema.

Do not assume BOOLEAN.

---

# Data Types

Validate every translated query against the supplied PostgreSQL types.

Common mappings

| Oracle    | PostgreSQL                 |
| --------- | -------------------------- |
| VARCHAR2  | VARCHAR                    |
| NUMBER    | NUMERIC / INTEGER / BIGINT |
| DATE      | TIMESTAMP                  |
| TIMESTAMP | TIMESTAMP                  |
| CLOB      | TEXT                       |
| BLOB      | BYTEA                      |

Always defer to the provided PostgreSQL schema.

---

# Error Handling

Preserve

- exception behaviour
- business rules
- validation messages

Document behavioural differences.

---

# Validation Checklist

Every translated artifact should verify

- SQL executes successfully
- Schema compatibility
- Returned columns
- Returned data types
- Row counts
- Null behaviour
- Transaction behaviour
- Exception behaviour

---

# Human Review Required

Human review is mandatory when

- schema conflicts exist
- Oracle Packages require redesign
- unsupported Oracle features are encountered
- translation changes business behaviour
- performance optimisation is required

---

# Anti-Patterns

Avoid

- redesigning queries
- renaming schema objects
- optimising SQL during migration
- changing business rules
- changing transaction boundaries
- introducing ORM changes unrelated to migration

---

# Success Criteria

Translation is complete when

✓ SQL is PostgreSQL compatible

✓ Business behaviour is preserved

✓ Validation succeeds

✓ Tests pass

✓ Reviewer approval obtained

✓ Manual activities documented
