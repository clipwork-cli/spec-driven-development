# Oracle to PostgreSQL Migration Standard

**Version:** 1.0

---

# Purpose

This Engineering Standard defines the recommended approach for migrating a legacy Oracle-backed application to PostgreSQL while preserving existing business behaviour.

The objective is **not** to redesign the application.

The objective is to replace the persistence technology with minimal functional impact while improving maintainability and testability.

This standard is intended for use with the Spec-driven Development Engineering Framework.

---

# Applicability

Use this standard when

- migrating Oracle Database to PostgreSQL
- modernizing legacy .NET applications
- replacing Oracle client libraries
- migrating Oracle SQL to PostgreSQL SQL
- incrementally migrating existing applications

Do not use this standard for

- complete application rewrites
- schema redesign
- business process redesign
- ORM migration projects where database compatibility is not required

---

# Engineering Principles

Every migration should follow these principles.

1. Preserve business behaviour.
2. Prefer incremental migration.
3. Deliver independently testable business capabilities.
4. Minimise production risk.
5. Validate every migrated capability.
6. Produce engineering evidence.
7. Avoid unnecessary refactoring.

---

# Migration Strategy

Spec-driven Development performs migrations using **Vertical Business Slices**.

Do **not** migrate by application layer.

Avoid approaches such as

```
Repositories

↓

Services

↓

Controllers

↓

Database
```

Instead migrate complete business capabilities.

```
Capability

↓

Database Objects

↓

Repositories

↓

Services

↓

Tests

↓

Validation
```

Every completed capability should be deployable, reviewable and independently testable.

---

# Migration Unit

The smallest migration unit is one Business Capability.

Examples

- Asset Registration
- Asset Search
- Work Order Creation
- Reporting
- Notification

Each capability should produce one Specification.

---

# Repository Discovery

Repository Discovery must be completed before migration begins.

Required Repository Context

- Architecture
- Repository Structure
- Dependencies
- Testing
- Modernization Assessment

Required Runtime Context

- Business Capabilities
- Operations
- Runtime Flows
- Database Usage

Migration should never begin without sufficient repository understanding.

## PostgreSQL Schema

A translated PostgreSQL schema must exist before migration begins.

Schema translation is considered a manual engineering activity.

AI should never redesign the schema.

Schema inputs should be provided using:

```
.ai/context/repository/database/
```

for shared schema artifacts, and

```
.ai/specifications/<spec-id>/schema/
```

for capability-specific schema artifacts.

# Responsibilities

## Architect

The Architect should

- identify business capabilities
- determine migration units
- generate one specification per capability
- identify architectural risks

Specifications should not be organised by technical layers.

---

## Planner

The Planner should

- identify affected projects
- identify Oracle dependencies
- identify required PostgreSQL objects
- define migration sequence
- define testing strategy
- define rollback strategy

---

## Developer

The Developer should

- migrate only the approved capability
- preserve behaviour
- follow existing architecture
- minimise unrelated changes

---

## Reviewer

The Reviewer should validate

- specification compliance
- behavioural compatibility
- testing completeness
- documentation
- deployment readiness

# Database Object Migration

Every business capability should identify the database objects it depends on.

Examples

- Tables
- Views
- Stored Procedures
- Functions
- Packages
- Sequences
- Synonyms
- Inline SQL
- Triggers

Database objects should be migrated together with the capability that uses them.

---

# Stored Procedures

When stored procedures exist

AI may assist in translating them.

However

AI should validate translations against the provided PostgreSQL schema.

If required information is unavailable

report

```
Requires Human Confirmation
```

Do not invent schema objects.

---

# Views

Views should be translated using the supplied PostgreSQL schema.

Validate

- column names
- data types
- joins
- functions
- filters

Document unsupported Oracle features.

---

# Inline SQL

Inline SQL should be translated as part of the capability.

Validation should include

- syntax
- parameters
- transactions
- null handling
- pagination
- date functions

---

# Schema Ownership

Schema translation is outside the scope of AI.

Engineers remain responsible for

- table definitions
- indexes
- constraints
- partitioning
- performance optimisation

AI assumes the PostgreSQL schema represents the desired target state.

---

# Testing Strategy

Preferred approach

```
Testcontainers

↓

Start PostgreSQL

↓

Execute Feature Tests

↓

Validate Behaviour
```

Fallback

```
Developer starts PostgreSQL locally

↓

Docker

or

Docker Compose

↓

Run Integration Tests
```

When using the fallback approach

clearly document assumptions.

---

# Validation

Every migrated capability should validate

- functional behaviour
- repository queries
- inline SQL
- stored procedures
- views
- transactions
- concurrency
- exception handling

---

# Manual Activities

The following activities remain manual.

- PostgreSQL schema design
- Data migration
- Performance tuning
- Production cutover
- Deployment approval
- Business acceptance testing

AI may assist documentation but does not replace engineering ownership.

---

# Out of Scope

This standard does not cover

- schema redesign
- database performance tuning
- infrastructure provisioning
- production deployment
- data migration tooling

These activities should be handled independently.

---

# Deliverables

Every migrated capability should produce

- Feature Context
- Specification
- Decision Log
- Implementation Plan
- Tasks
- Test Strategy
- Rollback Strategy
- Review
- Evidence

---

# Success Criteria

A capability is considered migrated when

- business behaviour is preserved
- PostgreSQL compatibility is verified
- tests pass
- manual validation succeeds
- documentation is updated
- reviewer approval is obtained

Migration is complete when every business capability has successfully met these criteria.
